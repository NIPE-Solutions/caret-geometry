02 / Responsibility boundary

Geometry and positioning are different jobs.

Caret Geometry tracks the caret. Your positioning engine tracks the world around it.

03 / Why compose them?

Why doesn’t Floating UI solve this already?

Floating-positioning libraries answer: “Given this reference rectangle, where should the floating element go?” They handle placement, collision, scroll, resize and layout movement.

Inputs and textareas have no native caret element. The browser exposes a value and selection indices—not caretElement.getBoundingClientRect(). Caret Geometry supplies that missing reference.

04 / Correct integration

One live reference. Two update sources.

createCaretVirtualElement() provides live geometry.
observeCaretGeometry() detects caret-local changes.
autoUpdate() detects environmental changes.
computePosition() places the popup.

06 / Responsibility matrix

Caret Geometry deliberately stops at the caret rectangle.

Concern Caret Geometry Positioning / overlay layer
Locate input, textarea or editable caret ✓ —
Typing, selection and internal-control scroll ✓ —
Page/ancestor scroll and layout shift — ✓
Collision, flip and shift — ✓
Portal rendering and interaction semantics — Framework / application

Do I need Caret Geometry?

Popup next to the input box? No. Use the element directly.

Popup next to the caret inside it? Yes.

Need collision, flip or portals? Add a positioning or overlay layer.
